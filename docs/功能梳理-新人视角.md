## 功能1：回答满意度反馈闭环（👍/👎）

### 1.1 功能通俗介绍
每一条 AI 回答的右下角有两个小按钮：👍 和 👎。点一下表示「这条建议我满意/不满意」，再点一下同色按钮就是取消。
- **痛点**：以前 AI 推荐完就走，用户觉得不对劲也没有渠道表达；产品方也不知道哪些菜被嫌弃了。
- **给谁用**：所有用户。点赞多 = 方向对；点踩多 = 系统要改。点踩的菜名还会被「记住」，下次推荐时主动避开。

### 1.2 实现思路（非技术版）
像餐厅的「桌边评价卡」：
1. 你在卡片上打了勾/叉（前端把好评/差评记到这条回答上，页面立刻变色）；
2. 服务员把评价抄到总账本上（后端在「会话记录」里给这条回答贴上 up/down 标签，同时在一份独立的流水账里追加一条带时间戳的事件）；
3. 每周盘点一次总账（周统计接口：近 7 天几个赞、几个踩、被踩最多的是哪几道菜）；
4. 厨师长开火前先看差评榜（每次生成新推荐前，把「近期被踩的菜名」作为一条硬约束塞进给 AI 的指令里：这几道别再推了）。

### 1.3 技术选型与工具
- **FastAPI 路由**（`api/routes/session_route.py`）：与项目现有 API 风格一致，无新增框架；
- **两份数据存储（都是 JSON 文件，无数据库）**：状态本体存会话记录的 `feedback` 字段（跟着对话走），统计事件存 `data/answer_feedback.json`（独立流水，方便按时间窗统计）；
- **乐观更新**：前端先自己变色再问后端，失败才回滚——省一次等待感。

### 1.5 核心代码片段 + 逐行翻译
**后端切换语义（`sessions_store.py` L275-293）——「再点一次就是取消」的关键：**

```python
def patch_message_feedback(sid, record_id, rating):
    # 参数：会话 id、回答记录 id、rating 只可能是 'up' / 'down' / None（取消）
    with _lock:
        # 全局写锁：同一时刻只有一个请求能改会话文件，防止并发写坏 JSON
        data = _read_session(sid)
        if data is None:
            return False, None   # 会话不存在：告诉上层「没找到」
        for m in data["messages"]:            # 逐条翻找这条回答
            if m.get("id") != record_id:
                continue
            if rating is None:
                m.pop("feedback", None)       # None = 取消：直接删掉这个字段
            else:
                m["feedback"] = rating        # 否则贴上 'up' 或 'down' 标签
            _write_session(data)              # 立刻写回磁盘（原子替换）
            return True, m.get("feedback")    # 返回 (找到了, 现在的状态)
    return False, None                        # 翻完没找到这条回答
```

**被踩避让注入（`main.py` L125-135）——差评如何影响下一次推荐：**

```python
downs = recent_down_dishes()          # 从流水账统计近14天被踩最多的菜名（最多5个）
if downs:                             # 一个差评都没有就不注入，不浪费提示词
    prefix_parts.append(
        "【近期不满意菜品（用户点过踩，务必参考）】\n"   # 给 AI 的醒目标题
        f"{'、'.join(downs)}\n"                        # 菜名顿号连接，如：红烧肉、咸鱼
    )
if prefix_parts:
    human = "".join(prefix_parts) + "【以上为自动加载约束，以下是本次需求】" + human
    # 拼接后：约束块在用户原话前面，AI 会先看到「避雷清单」再看到需求
```

### 1.6 数据流向与交互

## 功能2：家庭画像二级视图与导入导出分享

### 2.1 功能通俗介绍
侧边栏第三个入口「家庭成员」，点进去是一个独立的家庭面板：能看到所有成员的卡片（小美/我），可以切换「当前为谁做饭」、左滑删除成员，还能把整个家庭画像**复制成一段文本**发给家人，家人粘贴后一键导入——两台设备的画像就同步了。
- **痛点**：家里多人共用一个应用时，爸爸的高血压、孕妇的忌口全糊在一起；换手机画像全丢。
- **给谁用**：家庭共用用户；换设备用户。

### 2.2 实现思路（非技术版）
像一本「家庭健康户口本」：
1. 点「家庭成员」翻开户口本（侧栏导航切换到面板视图，聊天区暂时让位）；
2. 每张卡片是一页（成员名 + 健康标签），点卡片 = 把「当前做饭对象」的指针切过去；
3. 「导出」= 把户口本打印成一段可复制的文本（带版本号防串格式）；「导入」= 对方粘贴后，系统按名字对号入座：同名就覆盖画像，新名字就添一页，户口本最多 8 页；
4. 「当前是谁」的指针在导入时**不动**——避免导入别人数据后莫名其妙给错人做饭。

### 2.3 技术选型与工具
- 数据：`data/family_profile.json`（成员数组 + active_id 指针），延续项目「JSON 即数据库」约定；
- 校验：Pydantic 模型（`MemberPayload`/`ImportPayload`）做入参体检——畸形数据进不来；
- 前端：纯 React 组件 + 剪贴板 API，无状态库、无路由库（视图切换靠父组件一个状态变量）。

### 2.5 核心代码片段 + 逐行翻译
**导入的合并语义（`preferences_route.py` L222-242）——同名覆盖、新名追加、上限 8：**

```python
@router.post("/profile/import")
def import_family(payload: ImportPayload):   # payload.members 已经过 Pydantic 校验
    family = _read_family() or _migrate({})   # 读户口本；空文件就初始化一份
    added = updated = 0
    for incoming in payload.members:          # 逐个处理带来的成员
        name = incoming.name.strip()          # 去首尾空格，避免「小美 」≠「小美」
        existing = next((m for m in family["members"] if m["name"].strip() == name), None)
        # ↑ 按名字找现有成员：找到 = 同一人
        if existing is not None:
            existing["profile"] = incoming.profile.model_dump()  # 同名：整份画像覆盖
            updated += 1
        else:
            if len(family["members"]) >= 8:   # 户口本满 8 页：拒绝并说明
                raise HTTPException(status_code=400, detail=f"家庭成员最多 8 人，「{name}」未导入")
            family["members"].append({"id": f"m_{uuid.uuid4().hex[:8]}", ...})
            # 新成员发一个随机 id（m_ + 8位16进制），绝不复用已删除的 id
```

```
导出：FamilyPanel[导出并复制] → GET /api/profile/export

导入：家人粘贴 → FamilyPanel[导入] → POST /api/profile/import body:{members:[...]}
```

## 功能3：健康护栏结论可视化

### 3.1 功能通俗介绍
AI 回答里会有「健康护栏」：比如「你孕期，这道菜的汞风险已核查」「你高血压，已把盐量降到 3g」。以前这些结论埋在文字里，用户看不见。现在回答顶部有一条**横幅**：全绿 =「本轮推荐已通过全部健康护栏」；有黄灯 = 黄色提醒条；护栏改动过菜谱 = 琥珀色「已按你的画像调整」。横幅下面还有小状态卡，每条护栏一张，图标区分通过/警示/调整。
- **痛点**：护栏在默默起作用但用户无感知——「它到底有没有考虑我的高血压？」
- **给谁用**：所有有健康约束的用户（这也是产品信任感的来源）。

### 3.2 实现思路（非技术版）
像食品包装上的「质检标签」：
1. 质检员（后端护栏系统）检验完会随货附一张检验单（JSON 里的 `guardrails` 数组，每条有 status 字段）；
2. 商店（前端）看检验单做汇总：全是「通过」贴绿色标；有一条「警示」贴黄色标；有「已替你改过」贴琥珀标；
3. 每条检验记录做成小卡片贴在标签下面，用户一眼看全。

### 3.3 技术选型与工具
- 前端纯 CSS 三态配色（青绿 pass / 珊瑚 warn / 琥珀 adjusted），沿用项目「墨色+青绿」设计语言；
- 无新依赖：横幅是纯计算（一次 reduce 得出最高警级别），状态图标复用现有 Icon 组件。

| 前端·横幅计算 | `frontend/web/src/components/InsightPanel.tsx` | `statusIcon()` L30；横幅判定 L75-95（`guardrail-banner` L82） |
| 前端·样式 | `frontend/web/src/index.css` | `.guardrail-banner.pass/.warn/.adjusted` |
| 后端·数据来源 | LLM 回答 JSON 的 `guardrails` 字段（agent 链路产出，本功能只做展示） | |

## 功能4：追问门控放宽（自然措辞直通）

### 4.1 功能通俗介绍
系统在生成推荐前会先检查：「我知不知道你的健康约束？」以前只有用户原话精确说出「我有高血压」才放行，否则反复追问「请问您有基础疾病吗」，很烦人。放宽后，**「妊娠期高血压」「孕18周」「血压偏高」「尿酸高」**这类日常说法都能直接被认出来，不再纠缠；同时「我没有高血压」不会被误判成「有高血压」。
- **痛点**：被门控追问 3 轮才放行，体验极差。
- **给谁用**：所有没填完整画像、习惯随口说的用户。

### 4.2 实现思路（非技术版）
像前台登记的「别名识别」：
1. 客人说「我尿酸高」——前台知道这就是「痛风」这一类（别名表：一个正式病名挂好几个俗称）；
2. 听的时候避开否定：「没有高血压」里的「高血压」不算数——只认**没被「没/无/非」挡在前面**的词；
3. 三路信息取并集：①个人资料页填的 ②这轮对话里自述的 ③注入上下文的画像前缀——三处任何一处覆盖了病名就放行；
4. 「备孕」特意不算「孕期」（营养建议差异大），宁可多问一句。

### 4.3 技术选型与工具
- **纯 Python 字符串匹配**，不引入 NLP 库——规则可解释、可单测、零误判黑箱；
- 别名表硬编码在函数里（7 类病 × 各 3-5 个别名），新增病名只需加一行。

| `agent_graph.py` | `_self_declared_conditions(user_text)` | L657-678 | 别名表解析自述 |
| `agent_graph.py` | `_hit_without_negation(text, phrase)` | L645-654 | 否定排除 |
| `agent_graph.py` | `_declared_covers(condition, declared)` | L640-642 | 双向子串模糊覆盖 |

### 4.5 核心代码片段 + 逐行翻译
**否定排除（`agent_graph.py` L645-654）——「没有高血压」不算数的机关：**

```python
def _hit_without_negation(text, phrase):
    start = 0
    while True:
        idx = text.find(phrase, start)      # 从 start 起找「高血压」出现的位置
        if idx < 0:
            return False                    # 找遍了没有 → 没声明
        # 检查命中点前面 2 个字符里有没有否定词
        if not any(neg in text[max(0, idx - 2) : idx] for neg in ("没", "无", "非")):
            return True                     # 前面干净 → 算一次真声明
        start = idx + 1                     # 前面有否定词 → 跳过这次，继续往后找
        # 为什么 ±2 字符：中文否定词都是单字且紧贴名词（「没有高血压」「无高血压」），
        # 取 2 字窗口足以覆盖；再宽反而会把「确诊高血压」这类无害前缀误伤
```

## 功能5：菜品实拍图后台补图队列

### 5.1 功能通俗介绍
AI 推荐菜谱时会配一张「实拍图」。以前图片生成失败，卡片就永远秃着。现在后台有一条**补图流水线**：发现哪张卡片缺图，就自动排队重新生成，生成好了悄悄把图挂回去，用户下次刷新就能看到——不用重新问一遍。
- **痛点**：图片 API 偶发失败/超时，失败即永久缺图。
- **给谁用**：所有用户（无感修复）。

### 5.2 实现思路（非技术版）
像餐厅「照片菜谱补拍」：
1. 服务员发现某道菜的菜单页没照片，登记到补拍单上（识别缺图项）；
2. 摄影师按单子逐张补拍（后台任务逐个调图片 API）；
3. 拍好一张就换一张（锁内按「菜名」定位卡片上的图槽位回写，不整页重写）；
4. 拍坏了就跳过这张，下次再排（失败不阻塞其他）。

```python
    previous = [light.rsplit(":", 1)[1] for light in windows["previous"] if light.startswith(label + ":")]

    if len(previous) < 2 or len(latest) < 2:
        trends[label] = "insufficient"     # 任一窗不足 2 个样本：诚实说「样本少」
        continue                           # 不硬给方向性结论
    previous_risk = sum(level in {"yellow", "red"} for level in previous) / len(previous)
    latest_risk   = sum(level in {"yellow", "red"} for level in latest)   / len(latest)
    # 风险率 = 黄灯+红灯 占比
    trends[label] = "improving" if latest_risk < previous_risk else ("worsening" if latest_risk > previous_risk else "stable")
```

## 功能7：周报 AI 小结（指纹缓存 + 重新生成）

### 7.1 功能通俗介绍
周报页顶部有一段「AI 小结」：像私人营养师看了你一周的账本后写的 3-5 句评语——「本周 22 餐，糖控制最稳；钠有 9 次黄灯……作为孕妇可以稍留意盐量」。数据没变就不重新写（秒开）；点「重新生成」它才重写一篇。
- **痛点**：统计数字是冷冰冰的，用户要的是「所以呢？」的一句话结论。
- **给谁用**：所有周报页用户。

### 7.2 实现思路（非技术版）
像「盖章生效的体检报告」：
1. 先把一周原始数据打包成「证据包」（餐数、常吃菜、红绿灯、趋势、被踩菜、健康条件）；
2. 给证据包算一个「指纹」（内容变指纹才变）；
3. 指纹和上次报告对得上 → 直接取旧报告（免重写）；对不上 → 请营养师（LLM）照证据包写新的，写完盖章存档；
4. 「重新生成」按钮 = 强制作废旧章重写；
5. 营养师请假（LLM 挂了）→ 诚实说「小结暂时没生成」，**绝不编一段假的**。

### 7.3 技术选型与工具
- LLM：项目统一的 `model_name.get_langchain_llm(resolve_provider())`（OpenAI 兼容接口，provider 自动选择）；
- 缓存：`data/weekly_summary.json` 存 `{fingerprint, ai_summary, ts}`，指纹 = 证据包 JSON 的 md5——**避免每次刷新都烧一次 LLM 调用**（实测命中 40ms / 重生成 48s）；
- 降级链：无数据 → `no_data`；LLM 异常 → `reason` 字段，前端隐藏卡片。

### 7.4 代码位置精准定位
| 层 | 文件路径 | 函数 | 行号 |
|---|---|---|---|
| 后端·证据包 | `api/routes/reports_route.py` | `_weekly_evidence()` | L259-294 |
| 后端·画像条件 | `api/routes/reports_route.py` | `_active_conditions()` | L244-257 |
| 后端·小结端点 | `api/routes/reports_route.py` | `weekly_summary(refresh: bool)` | L296-350 |
| 前端·客户端 | `frontend/web/src/api/client.ts` | `fetchWeeklySummary(refresh)` | — |
| 前端·卡片/按钮 | `frontend/web/src/components/WeeklyReportPage.tsx` | `summary` 状态 + `regenerate()` | — |

### 7.5 核心代码片段 + 逐行翻译（缓存核心）

```python

    evidence = _weekly_evidence()            # 打包本周证据（无数据返回 None）
    if evidence is None:
        return {"ai_summary": None, "reason": "no_data"}   # 诚实：没数据就不写
    fingerprint = hashlib.md5(
        json.dumps(evidence, ensure_ascii=False, sort_keys=True).encode("utf-8")
    ).hexdigest()
    # sort_keys=True：同样内容无论字段顺序如何，指纹必须一致
    if not refresh:
        try:
            cache = json.loads(_SUMMARY_CACHE.read_text(encoding="utf-8"))
            if cache.get("fingerprint") == fingerprint and cache.get("ai_summary"):
                return {"ai_summary": cache["ai_summary"], "cached": True}
            # 指纹相同 = 本周数据没变 → 秒回，省一次 LLM 调用
        except Exception:
            pass                             # 缓存文件坏了等同没缓存，走重生成
    # …… LLM 生成（失败返回 reason，成功写回缓存文件）
```

## 功能8：轻量 markdown 渲染器

### 8.1 功能通俗介绍
AI 长回答常带 markdown 记号（`## 标题`、`**加粗**`、`- 列表`）。以前聊天区照抄文本，用户看到一串星号井号。现在这些记号被**翻译成真正的排版**：标题变大变粗、重点词加粗、列表缩进。
- **痛点**：markdown 源码裸露 = 不专业 + 可读性差。
- **给谁用**：所有用户（历史+未来消息一次性受益）。

### 8.2 实现思路（非技术版）
像「按菜谱摆盘」而不是「把菜谱打印出来钉墙上」：
1. 回答按行切开，逐行认形态：井号开头=标题、短横/数字开头=列表项、其他=段落；
2. 连续列表行拼成一个列表块（散珠串成一串）；
3. 段内 `**词**` 挑出来变粗体；
4. **不认识的记号原样保留**——宁可原样显示也不猜错吞字；
5. 全程不拼 HTML 字符串，直接产出 React 元素——天然免疫 XSS。

### 8.3 技术选型与工具
- **手写 ~80 行 TSX 工具函数**，不引 `react-markdown`——前端依赖保持 4 个、零打包增量；
- 只支持 LLM 实际输出的最小子集，超出语法按原文显示。

### 8.4 代码位置精准定位
| 文件路径 | 位置 |
|---|---|
| `frontend/web/src/utils/richText.tsx` | `renderRichText(source): ReactNode` + 内部 `renderInline()` |
| `frontend/web/src/components/ChatArea.tsx` | message-text 渲染处接入 |
| `frontend/web/src/index.css` | `.message-text p / .rt-heading / ul ol` 排版规则 |

### 8.5 核心代码片段 + 逐行翻译（内联加粗）

```tsx
const BOLD_RE = /\*\*([^*\n]+)\*\*/g   // 匹配 **加粗**：星号对之间不允许星号和换行

function renderInline(text: string, keyPrefix: string): ReactNode[] {
  const nodes: ReactNode[] = []
  let last = 0
  BOLD_RE.lastIndex = 0
  let match: RegExpExecArray | null
  while ((match = BOLD_RE.exec(text)) !== null) {   // 逐个找 **…** 片段
    if (match.index > last) nodes.push(text.slice(last, match.index))
    // 两个加粗之间的普通文字：原样推入（不重组不翻译）
    nodes.push(<strong key={`${keyPrefix}-b-${match.index}`}>{match[1]}</strong>)
    // 加粗部分变成真正的 <strong> 元素；key 用位置编号帮 React 复用节点
    last = match.index + match[0].length            // 记住处理到了哪里
  }
  if (last < text.length) nodes.push(text.slice(last))  // 收尾的普通文字
  return nodes
}
```

### 8.6 数据流向与交互
```
message.text（含markdown） → renderRichText() → <p>/<ul>/<ol>/<strong> 节点树
  → ChatArea .message-text 容器 → css 排版（标题/列表缩进/段落间距）
  安全性：文本只作为 React 子节点输出，永不被当 HTML 执行 → 无 XSS 面
```

## 功能9：RAG 检索瞬态自愈（retry）

### 9.1 功能通俗介绍
系统的「查资料」能力（查《高血压食养指南》这类）偶尔会因底层组件抽风失败一次。现在查失败会**自动隔 0.4 秒再查一次**，多数能自愈——健康知识查询稳定了，测试不再随机红。
- **痛点**：偶发失败导致回答缺知识支撑、测试随机挂。
- **给谁用**：所有依赖知识库的用户 + 开发者。

### 9.2 实现思路（非技术版）
像「门卡刷不开就再刷一次」：
1. 第一次刷门（查向量库）报异常；
2. 等半拍（0.4 秒，给底层缓劲）；
3. 自动再刷一次——多数瞬态这一次就过；
4. 还失败才如实上报（绝不静默吞掉）；
5. **只有「报错」才重试**：正常返回但没查到结果不算失败，不浪费重试。

### 9.3 技术选型与工具
- 保留项目自研检索层（Chroma 向量 + BM25 混合 + cross-encoder 重排），只在外层加 2 次尝试包装；
- 标准库 `time.sleep(0.4)` 短退避，自愈延迟几乎无感。

### 9.4 代码位置精准定位
| 文件路径 | 函数 |
|---|---|
| `rag/retriever.py` | `search()`（新外层重试包装）+ `_search_once()`（原检索主体改名，逻辑未动） |
| `tests/test_rag_recall.py` | 3 个召回质量用例 |

### 9.5 核心代码片段 + 逐行翻译（重试外层）

```python
def search(self, query, n_results=3, *, filter=None, use_hybrid=None, use_rerank=None, transform=None):
    """检索入口：Chroma 偶发瞬态（如 RustBindingsAPI 初始化竞态）自动重试一次。"""
    last: SearchResult | None = None
    for attempt in range(2):                 # 最多试两次
        last = self._search_once(query, n_results, filter=filter, ...)
        # 原检索逻辑整体挪进 _search_once，一行没改——降低回归风险
        if not last.error:                   # 只有「报错的结果」才需要重试
            return last                      # 正常（哪怕空结果）直接返回
        if attempt == 0:
            time.sleep(0.4)                  # 第一次失败：等 0.4 秒
    return last                              # 第二次仍失败：如实上报错误
```

### 9.6 数据流向与交互
```
agent 工具层 nutrition_kb_search(query)
  → rag/retriever.search()
     ├─ 第1次 _search_once → 报错(瞬态) → sleep(0.4)
     ├─ 第2次 _search_once → 成功 → hits[]
  → SearchResult{hits:[{text, source(文档名), section(章节)}]} → 回答可溯源
```
### 9.7 特殊配置或部署步骤
无新增配置。知识库文档在 `kb/`（28 个指南/食养 md），向量索引在 `kb/chroma/`（项目已有构建脚本）。

| `sessions/{sid}.json` | `{session_id,title,messages:[{id,user_text,answer,feedback?,image_url?,answer_original?}]}` | 聊天链路/反馈/补图 | 全部功能 |
| `data/family_profile.json` | `{active_id, members:[{id,name,profile:{conditions[],allergies[],dislikes[]}}]}` | preferences 路由 | 门控/推荐/周报 |
| `data/answer_feedback.json` | `[{ts,sid,rec_id,rating,dish}]` | 反馈端点 | 周统计/避让注入 |
| `data/meals.json` | `[{ts,session,dish,lights[],guardrails}]` | 每次决策自动记账 | 周报聚合 |
| `data/weekly_summary.json` | `{fingerprint, ai_summary, ts}` | 小结端点 | 小结端点（缓存） |
| `data/feedback.json` | `[{ts,dish,rating:1-5,tags[],comment}]` | 吃后评价端点 | 周报建议 |
| `kb/` + `kb/chroma/` | 28 个指南 md + 向量索引 | 构建脚本 | RAG 检索 |

### 新增/变更接口速查
| 方法+路径 | 入参 | 出参关键字段 |
|---|---|---|
| POST `/api/sessions/{sid}/messages/{rec_id}/feedback` | `{rating:'up'\|'down'}`（同值再点=取消） | `{feedback}` |
| GET `/api/feedback/weekly` | — | `{up, down, down_dishes[≤3]}` |
| GET `/api/profile/export` | — | `{export:{app,version:2,active_id,members[]}}` |
| POST `/api/profile/import` | `{members:[…]}` | `{added, updated}`（≤8人，active_id 不变） |
| GET `/api/reports/weekly` | — | `{has_data, meals, top_dishes, lights, light_trends, guardrail_triggers, range, next_week_shopping, recommendations, feedback_summary}` |
| GET `/api/reports/weekly-summary?refresh=0/1` | refresh 强制重生成 | `{ai_summary\|null, cached?, reason?}` |
| POST `/api/reports/feedback` | `{dish, rating:1-5, tags?, comment?}` | 记吃后评价 |
