## 二、定稿正文（294 字符，可直接粘贴报名系统）

小膳管家是一个带健康护栏的家庭膳食决策智能体。一家人的口味与病情各不相同：菜谱App只搬菜谱，通用大模型会顺着错误前提开出与慢病、过敏冲突的菜单。它接收成员画像、冰箱照片或一句口述，由LangGraph状态机多轮推理，以27份膳食指南及相关标准为依据；输出前再由营养、过敏原、画像三层硬规则审计，命中即带出处打回重生成，过敏原违禁不出菜。一桌菜按每位成员分别裁决，是它的核心形态。实测10例硬禁忌对照，拦截数从0升至10；14例端到端首稿违禁率80%—86%，三轮闭环后残留0/10；护栏审计p50为0.17毫秒，检索recall@3为39/39。Web端已跑通，可直接用于每日三餐决策。

**字数核对**（`.tmp-draft9.py` 实测）：总字符 294 ／ 纯汉字 215。红线 300，余量 6 字符——

## 七、放进文档时的写法与版式（简介位于文档最前面）

### 7.1 写法：不用「【问题】【方案】…」这种标签

赛题原文是「**可**按照『问题-方案-效果-应用』的逻辑撰写」（`rules.txt` 第 88 行）——「可」是可选建议，不是格式要求。
写成四个带标签的段落，等于把内部写作提纲直接印在文档第一页：评委翻开文档看到的第一句话就是
「问题：一家人病情与口味各异……」，先抱怨再自证，读起来像填空题，不像作品陈述。

**结论**：四要素的**内核**必须齐（问题、方案、效果、应用各占一段），但**不贴标签**，用自然段落递进；
标签式只留给答辩 PPT 的提纲页。

| 正文 | 宋体 12pt，行距 1.5 倍，段后 8pt |
| 首行缩进 | **缩进 2 字符**（四段均为自然段落，遵循中文正文惯例） |
| 段落 | 每个要素独立成段（问题／方案／效果／应用），段间不空行，靠段后间距分隔 |
| 对齐 | 两端对齐（西文与数字自动断开，避免出现大空洞） |

### 三个必须一起修的格式缺陷（现稿同源问题）

1. **标题进不了自动目录**：`scripts/build_aic_docx.py` 第 28-45 行的 `heading()` 是「普通段落 + 手工加粗」，不是 Word 内置「标题 1」样式。Word 的自动目录域（`TOC \o "1-3"`）和导航窗格**只抓内置标题样式**——照现在的写法，文档里"有很多目录"，但「作品简介」和各个章节都不会出现在自动目录里。改用 `doc.add_paragraph(style="Heading 1")`，再把该样式的字体覆盖为黑体加粗黑色（否则是 Word 默认的蓝色 Calibri）。
2. **旧简介末尾有一句自曝**：同文件第 190 行「（本段约 290 字，提交前可再精简至 300 字内）」——这是给自己看的批注，**提交稿里必须删掉**。
3. **份数口径前后矛盾**：同文件第 187 行与第 352 行写「11 份国家权威食养指南与国标」，与 `kb/` 目录真实的 **27 份**不符，也与简介矛盾。评委会拿简介去对正文，必须全文统一为 27 份。

### 字数口径说明

- 报名系统栏位：按所选版本整段粘贴（A 版 294 ／ B 版 298 ／ C 版 288 字符，换行不计入）。
- 文档内分段后字符数不变，仍 ≤300 字——分段不占字数。
- 三种写法的观感对比图：`docs/参赛-作品简介-排版甲乙对照.png`（左下为标签式，可对照看出它为何像模板）；
  目录页版式：`docs/参赛-作品简介-版式预览.png`。

## 八、简介定下来之后：全文口径纪律与八章对照

简介是全文的「合同」。下面这张表的作用是：后面写每一章时，先回看它在为简介的哪一句背书——
不允许出现简介没说、正文却扩大了的能力，也不允许同一件事在简介和正文里用两种说法。

### 8.1 四组固定关键词（全文统一，不得换说法）

| 固定说法 | 不要写成 | 为什么 |
|---|---|---|
| 家庭膳食决策智能体 | 菜谱助手／营养助手／健康管家 交替使用 | 交替使用会被当成三个产品，评委会怀疑定位不清 |
| 一桌菜按每位成员分别裁决 | 各种自创同义说法 | 这是市场差异点，答辩也要用同一句 |
| 三层硬规则（营养、过敏原、画像） | 「两层硬规则」 | 会把规则引擎与编排节点 `verify_answer` 混为一谈 |
| 三档护栏终态（合规出菜／附警示放行／过敏原违禁拦截） | 「零容忍」「全部拦截」 | `degraded` 是附警示放行，写成全拦与实现不符 |

### 8.2 三张「不许漂移」的边界

1. **护栏审计 p50 = 0.17—0.41 毫秒只指确定性规则引擎**，不是端到端响应时间。检索链路 p50 17.4 秒（本机 CPU 口径）另算，两者不可混用或相加。
2. **「附近餐厅／在外点单」是演示数据**（`api/routes/nearby_route.py` 的 `source="mock"`）。简介已不提外卖人群；正文任何位置提到它，必须并排标注「演示数据」，否则演示时穿帮。
3. **健康合规率、任务完成率、单餐决策耗时**三组数字，在试点报告（10-25）出来前一律不写进任何章节；出来后按 `docs/参赛-试点计划.md` 已定口径回填（任务完成率 = 完成数 ÷（人数×6 项，T7 不计分母），「部分」按 0.5 计），不得改口径。

### 8.3 八章反推表（每章为简介的哪一句背书）

| 章节 | 回应简介里的 | 该章必须落到实处的证据 | 禁止漂移 |
|---|---|---|---|
| 一、项目概述 | 「带健康护栏的家庭膳食决策智能体」 | 一句话定位 + 三层架构图；真实家庭档案（孕期＋增肌＋共同忌口芹菜） | 不出现第二个产品名 |
| 二、需求分析 | 「一家人的口味与病情各不相同」 | 问卷与访谈（10-13 回收）；真实档案说明场景 | 回收前不写「N 人调研」结论 |
| 三、解决方案设计 | 「输入 → 编排 → 依据 → 三层审计 → 违规打回」 | `domain/nutrition_rules.py`、`allergen_rules.py`、`constraint_rules.py` 三层规则 + `agent/graph.py` 的 `verify_answer` 节点 + RAG 混合检索 | 不写「两层硬规则」；不把 `verify_answer` 说成规则层 |
| 四、项目实施 | 「接收成员画像、冰箱照片或一句口述」 | 三类输入对应的路由；甘特图（200+ 提交的真实时间线）；技术栈清单 | 语音未配置时必须标「不可用」；mock 能力如实标注 |
| 五、测试与验证 | 「10 例对照 0→10」「三轮后 0/10」「recall@3 39/39」「护栏审计 p50」 | `docs/参赛-测试报告.md`（每个数字附复跑命令） | 每个数字必须带样本量与指标含义；不得改口径 |
| 六、应用效果与成果 | 「Web 端已跑通，可直接用于每日三餐决策」 | 用户试点（10-11~10-18 执行、10-25 报告）；反馈闭环数据管道 | 试点前不写完成率／满意度；附近餐厅标演示数据 |
| 七、总结与展望 | 「一桌菜按每位成员分别裁决」 | 三个算法核心 + 已知限制清单（单机演示态、本地 JSON 存储、14 例小样本、17.4s 为 CPU 口径） | 移动端／云部署必须写成「后续方向」，不得写成现状 |
| 八、附录 | 简介里的每一个数字 | 测试报告、算法实验数据、27 份资料清单与出处 | 附录新增数字后，同步回查简介与第五、六章 |

**用法**：改完任何一章，回这张表核一遍——如果某一章出现了简介里没有的能力、或与简介不同的口径，二者必须有一处改掉。
