### 1.1 Python 环境隔离：venv vs conda 怎么选

`📌 必学点`
- **结论先用 venv**：你已经在 ai_prvo 用 conda 也没问题，但投实习时对方问"怎么隔离依赖"答 venv + requirements.txt 比 conda 更主流
- `python -m venv .venv` → `source .venv/bin/activate`（Win: `.venv\Scripts\activate`）
- 一个项目一个 venv，**永远不要全局 pip install**

`⚠️ 常见坑`
- conda 和 venv 混用会冲突（base 环境的 site-packages 会被 venv 继承一部分）
- .venv 目录一定要加进 .gitignore

`🔗 参考`
- Python 官方 venv 文档：https://docs.python.org/3/library/venv.html

### 1.2 依赖锁定：requirements / poetry / uv

`📌 必学点`
- **入门选 requirements.txt**：`pip freeze > requirements.txt`，写进 README 让人 `pip install -r requirements.txt`
- 进阶选 **uv**（极快，10x pip 速度），是目前新项目主流
- poetry 适合需要发布库的项目，做应用选 uv 更轻
- **一定要锁版本**：`langchain==0.3.7` 不要写 `langchain`，否则下次装版本漂移直接崩

`⚠️ 常见坑`
- LangChain 生态分很多包：`langchain-core` / `langchain` / `langchain-community` / `langchain-openai` / `langchain-anthropic` ... 混装容易重
- 不要把 `torch` 锁死，PyTorch 大版本变更经常炸

`🔗 参考`
- uv 文档：https://docs.astral.sh/uv/

### 1.3 .env + config.py + model_client.py 分层（你的工程化 checklist）

`📌 必学点`
- `.env` 只放 secrets（API_KEY / DATABASE_URL），**不要进 git**
- `config.py` 负责读 .env 并定义 dataclass / pydantic-settings 强类型配置
- `model_client.py` 负责造 LLM 客户端实例（你 ai_prvo 的 `model_name.py` 已经是这层）
- 调用方永远不直接 `os.getenv`，只 `from config import settings`
- **双兜底**：函数 `get_llm(provider: str | None = None)` → 有参用参，无参读 env

```
调用方 → model_client.get_llm() → config.LLM_PROVIDER (env) / 参数覆盖
                              ↓
                       provider 路由表 (gpt / deepseek / qwen)
                              ↓
                       ChatOpenAI(base_url=..., api_key=...)
```

`⚠️ 常见坑`
- .env.example 要进 git，但 .env 不进 → 写好两份
- 配置项命名要统一大小写，建议全大写：`OPENAI_API_KEY` / `DEEPSEEK_API_KEY`
- **绝对不要在代码里写死 API key**，会被扫到泄密

`🔗 参考`
- pydantic-settings：https://docs.pydantic.dev/latest/concepts/pydantic_settings/

### 1.4 Provider 切换底座（你已做，补"多模型路由"概念）

`📌 必学点`
- 你 ai_prvo 已经有 `gpt` / `deepseek` 两家切换，**比赛亮点是"按任务路由"**（轻任务走 deepseek-chat，强任务走 gpt-4o）
- 路由策略可基于：任务类型 / 输入长度 / 预估 token / 预算上限
- 实现：在 `model_client.py` 维护一个 `MODEL_REGISTRY: dict[task_type, model_name]`
- **任务自适应动态模型路由**（你 user_memory 里的"竞赛答辩亮点"） = 把"该用哪个模型"的决策**自动化**，而不是写死在 prompt 里

```python
# 推荐写法（你已有底座的话加一层即可）
TASK_MODEL_MAP = {
    "summarize": "deepseek-chat",        # 便宜够用
    "extract":   "deepseek-chat",
    "plan":      "gpt-4o",                # 强推理
    "write":     "gpt-4o",
    "default":   "deepseek-chat",
}

def get_llm_for_task(task_type: str, **overrides):
    name = TASK_MODEL_MAP.get(task_type, TASK_MODEL_MAP["default"])
    return get_llm(provider=name, **overrides)
```

`⚠️ 常见坑`
- 不同模型的 function calling schema 略有差异，跨 provider 时要测
- 流式行为不一致（DeepSeek 流式更"卡顿"是因为 token 节奏问题，不是 bug）
- 同一个 deepseek base_url 既能跑 chat 又能跑 embedding 吗？答：不能，要看文档

`🔗 参考`
- LangChain Chat Model 抽象：https://python.langchain.com/docs/concepts/chat_models/

### 1.5 LangSmith 接入（实习加分 / 比赛必装）

`📌 必学点`
- LangSmith 是 LangChain 官方的 tracing 平台，能看到每次 LLM 调用的 prompt / response / token / 耗时
- 接入只要 4 个环境变量：`LANGCHAIN_TRACING_V2=true` / `LANGCHAIN_API_KEY` / `LANGCHAIN_PROJECT` / `LANGCHAIN_ENDPOINT`
- **不装 LangSmith 等于裸奔**：比赛答辩时评委问"你怎么 debug agent 跑偏的"你能直接甩 LangSmith 链接
- 免费额度足够学习和答辩用

`⚠️ 常见坑`
- 项目名要起好（比赛项目建议用统一前缀：`2026-XX比赛-xxx`）
- 不要把生产数据打进去，敏感场景关掉

`🔗 参考`
- LangSmith 文档：https://docs.smith.langchain.com/

### 1.6 日志与流式 tracing（你已会基础流式，补回调机制）

`📌 必学点`
- LangChain 有 `CallbackHandler` 抽象，能在 LLM 调用的 4 个时点注入：on_llm_start / on_llm_end / on_chain_start / on_chain_end
- LangSmith 背后就是用 CallbackHandler 实现的
- 你可以自己写一个 `ConsoleCallbackHandler` 把每个节点的输入输出打到 terminal
- **比赛答辩 demo 时**：开流式 + 开日志 = 评委能"看到 Agent 在思考"

`⚠️ 常见坑`
- 同步异步回调不要混用（`BaseCallbackHandler` 同步，`AsyncCallbackHandler` 异步）
- 在生产环境关掉 verbose，只在 debug 时开

`🔗 参考`
- Callbacks：https://python.langchain.com/docs/concepts/callbacks/

## 2. LangChain 核心（对标视频 5 节）

> 标：`【必学】`（多数已会，重点查漏）
> 视频对应：5. LangChain（5.1 - 5.20 模型 API / 核心模块 / 三种调用方式）
> 你状态：ChatPromptTemplate / Pydantic Parser / LCEL / @tool / bind_tools 都会

### 2.1 Model I/O：ChatModel / Embeddings / 多模态

`📌 必学点`
- LangChain 把模型抽象成 `BaseChatModel`，所有厂商的对话模型都继承它（你已用 ChatOpenAI）
- Embeddings 是另一类（`Embeddings`），输入 string 输出 `list[float]`，是 RAG 的核心
- 多模态：`ChatOpenAI` 支持 `image_url` content block；本地多模态用 `ChatOllama` + 视觉模型
- **实习面试必问**："为什么 LangChain 要自己抽象一层？" → 答：解耦，切换厂商不改业务代码

`⚠️ 常见坑`
- `temperature=0` 不等于完全确定性，只是采样更"贪心"
- 多模态模型对图片大小有限制，超大会自动压缩（细节丢失）

`🔗 参考`
- Chat Models：https://python.langchain.com/docs/concepts/chat_models/

### 2.2 提示词体系（你已会基础，补 MessagesPlaceholder / partial）

`📌 必学点`
- `ChatPromptTemplate.from_messages([...])` 接受 `(role, template)` 元组列表
- `MessagesPlaceholder("history")` 是动态插多轮历史的"槽位"，配合 LangGraph 的 `MessagesState` 用
- `prompt.partial(role="chef")` 预填充变量，避免每次 invoke 都传
- Few-shot：在 messages 列表里塞几组 `(human, ai)` 配对，效果立竿见影
- **SystemMessage 是控制 LLM 行为最有效的一招**，比写在 user prompt 里强 10 倍

`⚠️ 常见坑`
- Prompt 里的变量名要和 `prompt.invoke({...})` 的 key 一致
- 模板里写 `{}` 要转义成 `{{}}`（LCEL 用 Python 格式化语法）
- Prompt 写得太长会稀释注意力，把硬规则放最前

`🔗 参考`
- Prompts：https://python.langchain.com/docs/concepts/prompt_templates/

### 2.3 Output Parser（Pydantic 你已会 / JSON / 自动重试）

`📌 必学点`
- `PydanticOutputParser` 你已会，重点是 `get_format_instructions()` 拼进 prompt
- `JsonOutputParser` 不用 schema 时用，要求 LLM 输出合法 JSON
- **自动重试机制**：用 `with_retry()` + 自定义 validator；或者用 LangGraph 加一个"解析失败回炉重试"节点
- `OutputFixingParser` 能自动修 LLM 输出的小错（缺逗号、多引号）

```python
from langchain.output_parsers import OutputFixingParser
fixed = OutputFixingParser.from_llm(parser=chef_parser, llm=cheap_llm)
```

`⚠️ 常见坑`
- 模型有时会输出 markdown 代码块包裹的 JSON（` ```json ... ``` `），要 strip 掉
- Pydantic schema 的 description 是给 LLM 看的"字段说明"，写清楚能极大提升解析成功率

`🔗 参考`
- Output Parsers：https://python.langchain.com/docs/concepts/output_parsers/

### 2.4 LCEL 管道（| 组合 / .assign / RunnableParallel）

`📌 必学点`
- `|` 是 `Runnable.__or__` 语法糖：`(prompt | llm | parser).invoke(input)` 等价于手写三步
- `.assign()` 给 Runnable 字典"加字段"，不改原 dict 结构
- `RunnableParallel({"a": chain_a, "b": chain_b})` 并行执行多个链
- `RunnablePassthrough.assign(context=retriever)` 是 RAG 的标准入口写法
- **所有 LCEL 组件都是 Runnable**，意味着 stream / async / batch / config 都能直接用

`⚠️ 常见坑`
- LCEL 的 stream 行为：默认按 LLM token 流式流出来，但前面的 Runnable 不会流
- 不要在 LCEL 里直接调 `print`，会破坏流式

`🔗 参考`
- LCEL：https://python.langchain.com/docs/concepts/lcel/
- Runnable 接口：https://python.langchain.com/docs/concepts/runnables/

### 2.5 三种调用方式：invoke / stream / batch / async

`📌 必学点`
- `invoke(input)` 同步单次，返回完整结果
- `stream(input)` 同步流式，yield chunk
- `batch([input1, input2])` 批量，**会并行**
- `ainvoke / astream / abatch` 异步版本（FastAPI / WebSocket 必备）
- `astream_events` 是最详细的流式，会 yield 每个 Runnable 节点的事件，**比赛 demo 神器**

`⚠️ 常见坑`
- 同步异步混用会 deadlock（asyncio 上下文里调同步 LLM 会卡住）
- 批量太大要分批，OpenAI 有 2048 input 上限

`🔗 参考`
- LangChain Streaming：https://python.langchain.com/docs/concepts/streaming/

### 2.6 Memory：原生气 vs 你的 sessions/*.json

`📌 必学点`
- LangChain 原生 `ConversationBufferMemory` 已经被弃用（0.1+ 推荐用 LangGraph + MessagesState）
- 你 ai_prvo 用的 `sessions/*.json` **比原生 Memory 更好**：可序列化、可编辑、可版本管理
- 模式上两者殊途同归：原生气是"链的副作用"，你是"业务层显式管理"
- **比赛亮点**：你这是"自己实现了一套 session 管理"，比直接用 LangChain 内存更能讲

`⚠️ 常见坑`
- 历史太长会爆 token 窗口，要做摘要（用 `condense_history` 节点，你已会）
- JSON 文件并发写会冲突，要加锁或换 SQLite

`🔗 参考`
- LangGraph Memory：https://langchain-ai.github.io/langgraph/concepts/memory/

### 2.7 Callback 与 tracing 原理

`📌 必学点`
- `CallbackHandler` 4 个核心时点：start / end / error / text（流式）
- 实现 `BaseCallbackHandler` 子类，把想打的日志塞进对应方法
- LangChain 自带 `StdOutCallbackHandler` / `FileCallbackHandler`
- 比赛 demo 开 `verbose=True` + `StdOutCallbackHandler` 能让评委"看到 LLM 在想"

`⚠️ 常见坑`
- 自定义 Callback 里抛异常会打断主链，要 try/except 保护
- 异步链用 `AsyncCallbackHandler`

`🔗 参考`
- Callbacks：https://python.langchain.com/docs/concepts/callbacks/

### 3.1 提示词模板分类（6 个变体）

`📌 必学点`
- `PromptTemplate`：纯字符串，最老
- `ChatPromptTemplate`：消息列表，主流
- `FewShotPromptTemplate` / `FewShotChatMessagePromptTemplate`：few-shot 套娃
- `PipelinePromptTemplate`：把多个 prompt 拼装（system + user 分开写再合）
- `ChatMessagePromptTemplate`：自定义 role
- **实战中 90% 场景用 ChatPromptTemplate + MessagesPlaceholder 就够了**，别复杂化

`⚠️ 常见坑`
- 套娃太深会看不清最终 prompt 长啥样 → 写个 `print(prompt.format(...))` debug
- Few-shot 例子挑有代表性的，不要堆 5+ 个

`🔗 参考`
- Prompt 模板：https://python.langchain.com/docs/concepts/prompt_templates/#fewshotprompttemplate

### 3.2 Document Loaders（多格式）

`📌 必学点`
- 每个 Loader 接受一个"源"（路径/URL/对象），返回 `list[Document]`
- 常用：`TextLoader` / `PyPDFLoader` / `UnstructuredMarkdownLoader` / `CSVLoader` / `WebBaseLoader` / `NotionDBLoader`
- `Document` 有 `page_content`（文本）+ `metadata`（dict，如 `{"source": "x.pdf", "page": 3}`）
- **metadata 决定你能做多聪明的过滤**：存了 source 就能"只看 x.pdf"，存了 page 就能"跳到第 3 页"

`⚠️ 常见坑`
- PDF 加载用 `PyPDFLoader` 拆页 / `UnstructuredPDFLoader` 保留结构，按需选
- 中文 PDF 用 OCR 需要换 loader（`PaddleOCRLoader` / `RapidOCRLoader`）
- Web loader 拿到的 HTML 要清洗，否则会带一堆标签

`🔗 参考`
- Document Loaders：https://python.langchain.com/docs/concepts/document_loaders/

### 3.3 Text Splitters：chunk 切法对召回影响巨大

`📌 必学点`
- **核心原则**：chunk 不能太大（占 token / 噪声多），不能太小（语义断）
- `RecursiveCharacterTextSplitter`：按 `[\n\n, \n, 。, , ,空格]` 递回切，**默认首选**
- `TokenTextSplitter`：按 token 数切，**给 LLM 算成本时用**
- `MarkdownHeaderTextSplitter`：按 markdown 标题切，**保留结构**（比赛大杀器）
- `SemanticChunker`：按 embedding 相似度切（实验性，效果不一定好）
- **典型参数**：`chunk_size=500`, `chunk_overlap=50`，先按这个跑，召回差再调

`⚠️ 常见坑`
- `chunk_overlap` 不能为 0，否则边界处的句子会丢
- 中文逗号/句号和英文不一样，要用 `RecursiveCharacterTextSplitter(chunk_separators=[...])` 显式指定
- 不要拿整个 PDF 扔进去让 LLM 处理，先切

`🔗 参考`
- Text Splitters：https://python.langchain.com/docs/concepts/text_splitters/

### 3.4 Embeddings 模型选型

`📌 必学点`
- Embedding = 文本 → 向量（768/1024/1536/3072 维）
- 选型看三个维度：**维度 / 性能 / 中文支持**
- 推荐（2025-2026）：

| 模型 | 维度 | 优势 | 适用 |
|---|---|---|---|
| `text-embedding-3-small` (OpenAI) | 1536 | 通用强 | 有 OpenAI key |
| `BAAI/bge-m3` | 1024 | 中文顶配，多语言 | 本地 / 自部署 |
| `BAAI/bge-large-zh-v1.5` | 1024 | 中文 SOTA | 本地 |
| `moka-ai/m3e-base` | 768 | 轻量中文 | 资源紧 |
| `text-embedding-v3` (Qwen) | 1024 | 中文 + 长文本 | 阿里生态 |

`⚠️ 常见坑`
- **切向量库后不能再换 embedding**（维度对不上），选定就别动
- BGE 模型要带查询前缀：`query: xxx`，文档不加，**反了召回腰斩**
- 跑本地 embedding 需要 GPU，CPU 跑 BGE-large 一句要 100ms+

`🔗 参考`
- HuggingFace MTEB 排行榜：https://huggingface.co/spaces/mteb/leaderboard

### 3.5 Vector Stores 对比表

`📌 必学点`

| 库 | 部署 | 适用 | 优 | 缺 |
|---|---|---|---|---|
| **FAISS** | 本地/嵌入 | 一次性小数据集（<100w） | 极快、轻量 | 不支持 metadata 过滤（要自己拼） |
| **Chroma** | 本地 | 学习/demo | 易用、sqlite 友好 | 生产不够稳 |
| **Qdrant** | 本地/服务 | 生产 | 强、过滤好、支持混合检索 | 要起服务 |
| **Milvus** | 分布式 | 大数据 | 海量扩展 | 重、运维贵 |
| **pgvector** | Postgres 扩展 | 已有 PG | 复用 DB | 性能中等 |
| **Pinecone** | 云 | 不想运维 | 省心 | 贵、不可控 |

`⚠️ 常见坑`
- 学习阶段**先用 FAISS 或 Chroma**，别一开始上 Qdrant
- 生产要"持久化 + 可重启不丢"，FAISS 本身不持久，要 `faiss.write_index`
- 混合检索（BM25+向量）只有部分库原生支持（Qdrant / Elasticsearch）

`🔗 参考`
- Vector Stores 总览：https://python.langchain.com/docs/concepts/vectorstores/

### 3.6 Retriever 基础

`📌 必学点`
- `vectorstore.as_retriever()` 把向量库包成 Retriever 接口
- `search_type`：similarity（默认）/ mmr（最大边际相关性，去重）/ similarity_score_threshold
- `search_kwargs={"k": 4}` 召回 top-k
- **MMR 推荐**：默认 4 条里有 3 条在说同一件事，MMR 会主动分散

`⚠️ 常见坑`
- k 不是越大越好，>10 后 LLM 注意力散
- threshold 太严会召不到，太多会带噪声

`🔗 参考`
- Retrievers：https://python.langchain.com/docs/concepts/retrievers/

## 4. RAG 专题（视频未单列，单独补强）

> 标：`【必学+比赛加分】`
> 视频对应：视频里没单列 RAG（属于 LangChain 应用层），但**这是你目前最关键的缺口**
> 你状态：RAG 三件套（embedding/vector store/retriever）都没用过

### 4.1 最小可跑 RAG 链路

`📌 必学点`
- 5 步：load → split → embed → store → retrieve → generate
- 最后一步"generate"就是 LCEL 管道：`context | prompt | llm | parser`

```python
# 最小 RAG（10 行）
from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_community.vectorstores import FAISS

docs = TextLoader("kb.txt").load()
chunks = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50).split_documents(docs)
db = FAISS.from_documents(chunks, OpenAIEmbeddings())
retriever = db.as_retriever(search_kwargs={"k": 4})

from langchain_core.runnables import RunnablePassthrough
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_template("基于上下文：{context}\n回答：{question}")
rag = ({"context": retriever, "question": RunnablePassthrough()} | prompt | ChatOpenAI(model="gpt-4o-mini"))
print(rag.invoke("xxx 是什么？"))
```

`⚠️ 常见坑`
- `retriever` 接受的是 `str`（query），返回 `list[Document]`，但 LCEL 管道要的是 `str` context → 需要 `retriever | (lambda docs: "\n".join(d.page_content for d in docs))`
- 中文 kb 一定要用支持中文的 embedding

`🔗 参考`
- RAG Tutorial：https://python.langchain.com/docs/tutorials/rag/

### 4.2 Hybrid 检索（BM25 + 向量）+ Reranker

`📌 必学点`
- **BM25**：传统关键词检索，对专有名词/代码/英文术语召回比向量好
- **向量**：对语义、 paraphrase、跨语言召回好
- 混合 = `0.5 * BM25_score + 0.5 * vector_score`，互补
- **Reranker**：粗排取 top-50 → reranker 重排取 top-4 给 LLM
- 推荐 reranker：`BAAI/bge-reranker-large` / `Cohere Rerank 3`（API）

```python
# LangChain 混合检索
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever

bm25 = BM25Retriever.from_documents(chunks)
vec = db.as_retriever()
hybrid = EnsembleRetriever(retrievers=[bm25, vec], weights=[0.5, 0.5])
```

`⚠️ 常见坑`
- BM25 对中文要分词，LangChain 的 BM25Retriever 英文分词好，中文要加 jieba
- Reranker 是重模型（BGE-reranker-large 1.5G），CPU 慢

`🔗 参考`
- EnsembleRetriever：https://python.langchain.com/docs/how_to/ensemble_retriever/

### 4.3 查询改写 / Multi-Query / Step-Back

`📌 必学点`
- 用户问题往往模糊（"那个东西怎么搞"），先改写再检索能提升召回
- **Multi-Query Retriever**：让 LLM 生成 3-5 个改写问题，对每个都检索后合并去重
- **Step-Back Prompt**：先让 LLM 抽象问题（"用户实际想问什么"）再去检索
- **Query Decomposition**：把复杂问题拆成子问题分别检索

`⚠️ 常见坑`
- Multi-Query 会增加 LLM 调用次数（1 次改写 + N 次检索），成本翻倍
- 改写 prompt 要明确"保持原意，只换表达"，否则会跑偏

`🔗 参考`
- MultiQueryRetriever：https://python.langchain.com/docs/how_to/MultiQueryRetriever/

### 4.4 上下文压缩 / LongContextReorder

`📌 必学点`
- `ContextualCompressionRetriever`：在 retriever 后面包一层"压缩器"，只留和问题相关的句子
- `LongContextReorder`：检索结果在 prompt 里**放在最后**，避免"中间遗忘"效应（Lost in the Middle）
- 配合使用：检索 → 压缩 → 重排 → 给 LLM

`⚠️ 常见坑`
- 压缩器本身是 LLM 调，又多一次 LLM call
- 重排对长 prompt 才有用（>4 个 chunk）

`🔗 参考`
- Contextual Compression：https://python.langchain.com/docs/how_to/contextual_compression/

### 4.5 父子文档检索 / 元数据过滤

`📌 必学点`
- **父子文档**：检索时用小 chunk（精确），但给 LLM 看时换成大 chunk（上下文完整）
- LangChain 用 `ParentDocumentRetriever`，底层要配 `InMemoryStore` 存原始大块
- **元数据过滤**：建索引时给每条 document 打标（`{"category": "法律", "date": "2024"}`），检索时 `filter={"category": "法律"}`
- 比赛亮点："支持按时间/类别/来源过滤的 RAG"

`⚠️ 常见坑`
- 元数据过滤的语法因向量库而异（Chroma / Qdrant / FAISS 各有不同）
- 父子文档要建两层 chunk，存储复杂度↑

`🔗 参考`
- ParentDocumentRetriever：https://python.langchain.com/docs/how_to/parent_document_retriever/

### 4.6 Self-RAG / CRAG 思路（比赛答辩高级亮点）

`📌 必学点`
- **Self-RAG**：让 LLM 自己判断"这段检索结果是否相关、是否需要重新检索"
- **CRAG**（Corrective RAG）：检索结果不够好时主动用 web search 补救
- 实现模式：在 LangGraph 里加一个 `grade_documents` 节点，让 LLM 给每条 chunk 打分，< 阈值的丢掉
- **评委提问"你怎么处理幻觉"** → 答 Self-RAG 评分机制，杀手锏

`⚠️ 常见坑`
- Self-RAG 评分 prompt 要写好，否则 LLM 乱打分
- 评估 Self-RAG 效果要专门测，光看表面答得对不算

`🔗 参考`
- Self-RAG 论文：https://arxiv.org/abs/2310.11511
- CRAG 论文：https://arxiv.org/abs/2401.15884

### 4.7 RAG 评估：Ragas 三件套（比赛答辩硬通货）

`📌 必学点`
- RAG 评估分 4 个核心指标（用 Ragas 一行代码算）：
  - **Faithfulness**：答案是否忠于检索上下文（防幻觉）
  - **Answer Relevancy**：答案是否切题
  - **Context Precision**：检索的 chunk 有多少是真有用的
  - **Context Recall**：标准答案涉及的知识点被检索到的比例（要 ground truth）
- **比赛答辩时**：用 Ragas 跑一个 50 条 test set 拿分截图，比嘴上说"我做得好"强 100 倍
- `from ragas import evaluate` + `from datasets import Dataset`

`⚠️ 常见坑`
- Ragas 要 LLM 当裁判（一般用 gpt-4o），成本不低
- Context Recall 必须有 ground truth，标注成本高
- 评估结果有随机性（LLM 裁判会波动），要跑多次取平均

`🔗 参考`
- Ragas 文档：https://docs.ragas.io/

### 4.8 常见 RAG 坑清单

`📌 必学点`
- chunk 切太大：占 token、噪声多 → 用 500/50
- embedding 不匹配：混用 OpenAI 和 BGE 维度 → 选一个就锁死
- 忽略 rerank：top-4 全是同一主题 → 加 MMR 或 reranker
- 不存 metadata：无法过滤 → 建库时一定打标
- 没评估：不知道好不好 → 至少用 Ragas 跑一次
- 提示词太啰嗦：挤占 token → 把 RAG prompt 模板化
- 忘了加 source：用户问"哪里说的"答不上 → prompt 里强制要求引用 `[1][2]`

### 5.2 @tool / Pydantic schema / bind_tools

`📌 必学点`

```python
@tool
def search_recipe(keyword: str = Field(description="菜名或食材，如'红烧肉'")) -> str:

    ...
```

`⚠️ 常见坑`
- description 要写中文（如果用中文 prompt），英文 description LLM 容易理解错
- 参数不要超过 5 个，否则 LLM 选错率高

`🔗 参考`
- Tool 定义：https://python.langchain.com/docs/concepts/tools/

### 5.3 ToolNode 内部机制

## 6. LangGraph 核心与持久化（对标视频 8-9 节）

> 标：`【必学+查漏】`
> 视频对应：8. LangGraph 基础 + 9. 持久化（含 69-72 持久化演示）
> 你状态：循环图 + SqliteSaver 已会，缺 interrupt

### 6.1 StateGraph / State / TypedDict vs MessagesState

`📌 必学点`
- `State = TypedDict` 或 `BaseModel`，定义图的"全局状态"
- 你已用 `MessagesState`（langgraph 内置，只含 messages 字段）
- 复杂状态要自定义：`class State(TypedDict): messages: list; user_id: str; turn_count: int`
- 状态更新：节点函数返回 `dict`，LangGraph 自动 merge（默认覆盖，list 字段可配 reducer）

`⚠️ 常见坑`
- list 字段要配 `Annotated[list, add_messages]` 这种 reducer，否则会被覆盖
- 状态字段太多会变慢，控制在 10 个以内

`🔗 参考`
- StateGraph：https://langchain-ai.github.io/langgraph/concepts/low_level/

### 6.2 节点 / 边 / 条件边 / 回边

`📌 必学点`
- 节点：`def my_node(state) -> dict`
- 普通边：`add_edge("A", "B")` A 完必走 B
- 条件边：`add_conditional_edges("A", route_fn, {"B": "B", "C": "C"})`
- 回边：`add_edge("B", "A")` 形成循环（你已会）
- 起点：`add_edge(START, "A")`，终点：`add_edge("B", END)`

`⚠️ 常见坑`
- 条件边的 route_fn 返 string，要和 `add_conditional_edges` 的 mapping 对应
- 死循环：用 `recursion_limit` 兜底

`🔗 参考`
- Graph API：https://langchain-ai.github.io/langgraph/concepts/low_level/

### 6.3 Checkpointer 三件套

`📌 必学点`

| Checkpointer | 存储 | 适用 |
|---|---|---|
| `MemorySaver` | 内存 | 单元测试 |
| `SqliteSaver` | SQLite 文件 | 学习 / 单机（**你已用**） |
| `PostgresSaver` | Postgres | 生产 / 分布式 |
| `RedisSaver`（第三方） | Redis | 高速持久化 |

- 用法：`graph = builder.compile(checkpointer=SqliteSaver.from_conn_string("checkpoint.db"))`
- 每次 invoke 必须传 `config={"configurable": {"thread_id": "xxx"}}`

`⚠️ 常见坑`
- 同一 thread_id 会复用历史，测试时要换新 ID
- SqliteSaver 写入是同步的，并发高会卡

`🔗 参考`
- Persistence：https://langchain-ai.github.io/langgraph/concepts/persistence/

### 6.4 thread_id 与 get_state / update_state

`📌 必学点`
- `graph.get_state(config)` 看当前 thread 的状态快照
- `graph.get_state_history(config)` 看完整历史（时间旅行）
- `graph.update_state(config, {"messages": [new_msg]})` 手动改 state
- **比赛演示**：让评委"倒带"看历史轨迹，杀手锏

```python
config = {"configurable": {"thread_id": "user_001"}}
state = graph.get_state(config)
for s in graph.get_state_history(config):
    print(s.values, s.next, s.metadata)
```

`⚠️ 常见坑`
- `update_state` 会新建一个 checkpoint，不影响历史
- `get_state_history` 返回 generator，要 list() 才能复用

`🔗 参考`
- Time travel：https://langchain-ai.github.io/langgraph/concepts/time-travel/

### 6.5 时间旅行与回放

`📌 必学点`
- 从 `get_state_history` 选一个历史 checkpoint，**用它的 config 重新 invoke** → 状态从那个点继续
- 可做"撤销并重做"、"修改过去决策看后续"、"AB 测试同一个输入"
- **比赛亮点**：可视化时间线，评委能体验

`⚠️ 常见坑`
- 重放会创建新 checkpoint，不会覆盖历史
- 重放时如果状态有依赖外部数据，要确保外部数据没变

### 6.6 异常恢复：失败重跑 / Resume

`📌 必学点`
- 图运行时抛异常 → 节点失败 → checkpoint 记录"卡在哪"
- 重跑：传同样的 config 重新 invoke，LangGraph 自动从失败点继续（需要 checkpointer）
- **业务级 resume**：interrupt + 用户输入 → 继续

`⚠️ 常见坑`
- 节点函数一定要幂等（重跑不能有副作用）
- LLM 调用的 token 不会退钱，重跑成本高

### 6.7 interrupt_before / interrupt_after 人工审批（**你的缺口，比赛亮点**）

`📌 必学点`
- `compile(interrupt_before=["node_x"])` → 跑到 node_x 之前**暂停**，等外部命令
- `graph.invoke(None, config)` → 继续执行
- **典型场景**：
  - 发送邮件/支付前要人工确认
  - 删除文件前要确认
  - 工具结果异常时让用户裁决
- **比赛答辩杀手锏**：演示"Agent 自己识别到不能做的事，主动停下问用户"

```python
builder.add_node("send_email", send_email_node)
graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["send_email"]  # 发邮件前停
)

# 第一次跑
graph.invoke({"messages": [...]}, config)
# 弹出"是否发送"对话框给用户
# 用户确认后再跑
graph.invoke(None, config)  # 继续
```

`⚠️ 常见坑`
- interrupt 必须在 compile 时声明，不能动态开
- interrupt 后 state 已停在 node 之前，要从 state 拿上下文
- 多次 interrupt 要配合 `Command(resume=...)`

`🔗 参考`
- Human-in-the-loop：https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/

### 6.8 Command 与动态跳转

`📌 必学点`
- `Command(goto="node_x", update={"key": value})`：节点函数返回，跳转到指定节点并更新 state
- 用来做"动态分支"：根据 LLM 决策结果跳不同节点
- **比条件边更灵活**：决策逻辑可以放在节点里而不是纯函数

`⚠️ 常见坑`
- Command 的 goto 不能跳到不存在的节点
- Command + interrupt 配合做"审核后修改路径"

`🔗 参考`
- Command：https://langchain-ai.github.io/langgraph/concepts/low_level/#command

### 6.9 流式输出：astream / astream_events

`📌 必学点`
- `graph.stream(input, config, stream_mode="values")`：每节点结束 yield state
- `astream_events`：yield 所有 Runnable 事件（LLM start/end、tool start/end）→ **比赛 demo 神器**
- stream_mode 选 `"messages"` 可以 token 级流式

`⚠️ 常见坑`
- 同步 stream 会卡（每 yield 一次要等下次调用），用 `astream` 才能边生成边输出
- astream_events 输出很啰嗦，要按 `event["event"]` 过滤

`🔗 参考`
- Streaming：https://langchain-ai.github.io/langgraph/concepts/streaming/

### 7.1 分支 / 扇出（fan-out / Send）

`📌 必学点`

### 7.2 子图 Subgraph（**多 Agent 协作地基**）

`📌 必学点`
- 子图 = 一个完整的 StateGraph 作为另一个图的节点

`⚠️ 常见坑`
- 子图有独立 checkpointer 会和父图冲突，建议共用

`🔗 参考`

## 8. 多 Agent 编排与比赛亮点

> 标：`【比赛加分】`
> 视频对应：10+ 多 Agent 实战
> 你状态：单 Agent，没碰过

### 8.1 Supervisor 模式

`📌 必学点`
- 一个 supervisor（planner）节点：分析用户问题 → 决定调哪个 worker → 收结果 → 再决定下一步
- workers 是独立子图（research_agent / code_agent / write_agent）
- supervisor 用 LLM 决策（结构化输出 + Pydantic）
- 比赛亮点："我的系统是分层决策的，不是单点 LLM"

```
                    ┌─→ ResearchAgent
User → Supervisor ──┼─→ CodeAgent
                    └─→ WriteAgent
                          ↓
                       Supervisor
                          ↓
                        User
```

`⚠️ 常见坑`
- supervisor 决策要限制工具集（只让它选 worker，不要让它直接回答）
- worker 之间通信要走 supervisor，不要 worker 之间互调（避免死循环）

`🔗 参考`
- Multi-Agent：https://langchain-ai.github.io/langgraph/concepts/multi_agent/

### 8.2 协作模式：planning-execution-validation

`📌 必学点`
- 三段式：planner（拆解任务）→ executor（执行）→ validator（校验）
- validator 失败 → 回到 executor 重做，最多 N 次
- **比 Supervisor 更结构化**，比赛答辩有清晰的故事

`⚠️ 常见坑`
- 失败次数太多会爆 token，要设上限
- validator 写得过严会全部失败，过松会漏检

### 8.3 任务自适应动态模型路由（**你 user_memory 里的"竞赛答辩亮点"**）

`📌 必学点`
- 核心：**根据任务自动选模型**，不是人工事先决定
- 决策依据：任务类型、输入长度、预估难度、预算
- 实现方式（你 ai_prvo 已有底座，加路由层即可）：

```python
# model_router.py
TASK_MODEL_MAP = {
    "summarize":   ("deepseek-chat",     "cheap"),
    "extract":     ("deepseek-chat",     "cheap"),
    "classify":    ("deepseek-chat",     "cheap"),
    "plan":        ("gpt-4o",            "strong"),
    "write":       ("gpt-4o",            "strong"),
    "judge":       ("gpt-4o",            "strong"),
    "default":     ("deepseek-chat",     "cheap"),
}

def route(task_type: str) -> str:
    return TASK_MODEL_MAP.get(task_type, TASK_MODEL_MAP["default"])[0]

# 在 LLM 调用前
def my_node(state):
    task = state["task_type"]  # 前面节点已经分类好
    llm = get_llm_for_task(task)
    ...
```

`⚠️ 常见坑`
- 任务分类本身要消耗一次 LLM，要权衡（直接让 LLM 自报任务类型更省）
- 路由策略要可观测（LangSmith 里看每次用了哪个模型）

### 8.4 双兜底配置容错（**通用代码模板**）

`📌 必学点`
- 模式：**有参优先 + 无参读 env + 兜底默认值**
- 你 ai_prvo 已经在用，**抽象成通用装饰器**给所有 LLM 调用：

```python
# config_resolver.py
import os
from functools import wraps

def resolve_config(param_name, env_key, default=None):
    """装饰器：有调用参数用参数，无则读 env，再无则用 default"""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            if param_name in kwargs and kwargs[param_name] is not None:
                return func(*args, **kwargs)
            env_value = os.getenv(env_key, default)
            kwargs[param_name] = env_value
            return func(*args, **kwargs)
        return wrapper
    return decorator

# 用法
@resolve_config("provider", "LLM_PROVIDER", "deepseek")
def get_llm(provider: str | None = None, **kwargs):
    return ChatOpenAI(model=PROVIDER_MODEL[provider], **kwargs)

# 调用方
llm = get_llm()              # 读 env
llm = get_llm(provider="gpt") # 覆盖
```

`⚠️ 常见坑`
- env key 要起好名字（统一前缀：`LLM_` / `DB_` / `REDIS_`）
- 兜底值要合理（不要让"忘记配"导致用错模型）
- 写测试：模拟 env 缺失，验证兜底

### 8.5 Agent 评估：LangSmith / LangChain Evals

`📌 必学点`
- LangSmith 自带 dataset + evaluator，能跑批量评估
- 评估维度：答案正确性、工具调用是否合理、token 效率
- **比赛答辩**：拿评估报告截图展示
- LangChain Evals 库（`langchain.evaluation`）内置多种 evaluator

`⚠️ 常见坑`
- 评估需要 LLM 当裁判，又要钱
- test set 至少 30 条才有统计意义

`🔗 参考`
- LangSmith Evaluation：https://docs.smith.langchain.com/evaluation

### 8.6 成本-效果平衡

`📌 必学点`
- 不是所有调用都要 gpt-4o，"轻任务用轻模型"是实打实的省钱
- 一般分配：分类/提取/格式化用 deepseek-chat（便宜 50x），规划/创作/判断用 gpt-4o
- **比赛加分**：在 LangSmith 里统计每个模型的调用次数和成本，做成成本看板

`⚠️ 常见坑`
- 不要为了省钱让所有任务都走小模型，效果会崩
- 计费要看 input + output，**output 比 input 贵 3-4x**

### 11.3 常见坑清单

| 坑 | 现象 | 解决 |
|---|---|---|
| LangChain 版本漂移 | 代码上周跑得好好的今天炸 | 锁版本 `==0.3.7` |
| 同步异步混用 | `asyncio` 里调同步 LLM 卡死 | 全用 `ainvoke/astream` |
| RAG 召回差 | 答案不沾边 | 改 chunk size、加 rerank、换 embedding |
| Checkpoint 锁竞争 | 高并发写 sqlite 报 locked | 换 PostgresSaver |
| Function calling 不支持 | 旧模型直接不返 tool_calls | 换支持 FC 的模型 |
| Prompt 注入 | 用户在 input 里改 system 行为 | 严格分层 + 强 system 约束 + 工具白名单 |
| Token 爆 | 上下文太长报错 | 摘要节点 + 移除老消息 |
| Embedding 不匹配 | 检索召回全 0 | 检查维度、模型前缀（BGE 要加 `query:`） |
| LLM 裁判不稳定 | 评估结果每次不同 | 跑多次取平均 + 用温度 0 |
